# Scraper — Phase 0 capability & defect audit (2026-08-07)

Audit of the repo as it stands before session 1. Reproducible evidence: `tools/spec-audit/`
(`node audit.mjs`, `node negative.mjs`, `node statemachine.mjs`).

---

## 1. Current capabilities — what the system can actually do

**Executable capability: none.** There are 0 TypeScript files, no `apps/`, `services/`, or `packages/`,
no Prisma schema, no tests. Nothing in the repo can send, parse, store, or verify anything.

What exists is a **spec kit** — 1,225 lines of design docs plus four machine-readable artifacts:

| Artifact | State | Machine-readable? | Verdict |
|---|---|---|---|
| `docs/00`–`09` (10 files) | Complete, detailed | No | Strong; internally inconsistent in 6 places (§3) |
| `schema/playbook.schema.json` | Compiles under draft 2020-12 | **Yes** | Enforces almost nothing (§3, C2) |
| `schema/request-state-machine.md` | 13 states, 19 transitions | No (prose) | 3 structural gaps (§3, C4/C5/H1) |
| `playbooks/*.yaml` (5) | 5/5 parse, 5/5 schema-valid | **Yes** | 1 references a missing template |
| `templates/*.md` (3) | Substantive German legal prose | Partly | Not sendable as letters (§3, C6/H5) |
| `.env.example` | 22 keys, all providers stubbed | Yes | Consistent with `docs/02` interfaces |
| `package.json` | Declares pnpm workspaces | Yes | **Does not run** (§3, B1) |

**Design-level capability that is genuinely sound** — this is the part worth protecting:

- **The anti-stalker invariant holds structurally.** `subjectFields` is a closed enum
  (`legalName | dateOfBirth | addresses`). No free-text subject field exists anywhere in the schema,
  the five playbooks, or the three templates. The one rule that outranks all others is not merely
  documented, it is unrepresentable to violate in the artifacts that exist.
- **Escalation is human-gated in the transition graph.** `ESCALATED` has exactly one inbound edge,
  `humanSend`. Verified by reachability analysis, not by reading the prose.
- **The German legal prose is substantive and correctly grounded** — Art. 15(1)(g) source-by-category
  demand, Art. 21(2) framed as unconditional with the over-collection pushback, Art. 12(3) deadline
  asserted in all three. This is the highest-value content in the repo.

## 2. Test method

Three harnesses, since there is no code to test:

1. `audit.mjs` — YAML parse + JSON-Schema validation of all playbooks; template-existence and
   template-variable ↔ `subjectFields` binding checks; cross-document reference integrity; controller-slug
   consistency against the census; playbook semantic lints.
2. `negative.mjs` — 25 malformed playbooks that must never reach a send path, run against the schema.
3. `statemachine.mjs` — the state machine transcribed as a graph; dead-end and reachability analysis
   against the journeys the other docs require.

Result: **1 hard failure, 9 warnings, 15 checks passed** from (1); **23 of 25 must-reject cases accepted**
by (2); **4 structural problems** from (3).

## 3. Defects

### Blockers — session 1 hits these in the first ten minutes

**B1 · The declared toolchain does not run.** `package.json` sets `"packageManager": "pnpm@9"` and every
script is `pnpm -r <task>`, but workspaces are declared in the **npm-style `"workspaces"` array**. pnpm
discovers workspaces only from `pnpm-workspace.yaml`, which does not exist — so `pnpm -r build` resolves
zero packages even once code exists. `npm run build` currently exits via a corepack `loadSpec` error.
`apps/`, `services/`, `packages/` are all absent.
*Fix:* add `pnpm-workspace.yaml` with `packages: ['apps/*','services/*','packages/*']`; drop or keep the
npm array as documentation only.

**B2 · A shipped playbook references a template that does not exist.**
`playbooks/loeschung.generic-adresshaendler.yaml` → `template: art17-loeschung.de` →
`templates/art17-loeschung.de.md` is missing (the file carries its own `# TODO: add this template`).
One of the five example playbooks — the ones `PROMPT.md` step 4 says to wire — cannot render.

### Critical — spec contradictions that will be faithfully implemented as bugs

**C1 · The statutory clock can be started on something the guardrails say is not proof.**
`schema/request-state-machine.md` invariant 2 defines `provableSendConfirmed` as *"email accepted +
DKIM-aligned, **or** postal proof / Einwurf-Einschreiben receipt."* `CLAUDE.md` §6 and `docs/05` §6 both
say the opposite: *"Email alone is not proof of delivery for the statutory clock."*
The state machine is the file that gets implemented, so an implementer following it will set `deadlineAt`
from a DKIM accept, then escalate to a DPA on a deadline that was never legally established. This affects
every email-primary playbook — `werbewiderspruch.az-direct` (`registered: false`) and
`loeschung.generic-adresshaendler`. Flagged independently by `audit.mjs` as `CLOCK-PROOF`.
*This one needs your decision, not just a fix* — see §4.

**C2 · The schema is the only executable guard in the repo and it rejects nothing.** 23 of 25 malformed
playbooks were accepted. The most serious:

| Accepted playbook | Consequence |
|---|---|
| `humanReviewIfConfidenceBelow` **omitted entirely** | No human-review floor. This is the `docs/06` C4 anti-prompt-injection control. |
| `humanReviewIfConfidenceBelow: 0` | Parser output auto-decides `COMPLIED`/`REFUSED` at any confidence — the exact thing C4 forbids. |
| `recipient: {}` | Playbook with nothing to send to. |
| `primary: postal` + only `recipient.email` | Channel/recipient mismatch (schema has no conditional requirement). |
| `recipient.email: "not-an-email ### <<"` | No `format: email`, no pattern. |
| `escalation: {}` | Silent no-escalation; `escalation` is required but all of its properties are optional. |
| `compliedIf: {}` and `compliedIf.anyOf: [{lol:"wut"}]` | `$defs/condition.anyOf.items` is unconstrained `{"type":"object"}` — **the matcher syntax every real playbook actually uses is entirely unvalidated.** |
| `compliedIf` and `refusedIf` matching the same string | Contradictory outcome, silently. |
| `controller: "__PARAM__"`, `recipient.email: "__PARAM__"` | Unresolved placeholders are valid; only `active: false` stands between the generic erasure playbook and a live send. |
| `seatDpa: "LFDI_BAYERN_TYPO"` | Free string, no enum — a typo misroutes an Art. 77 complaint to the wrong authority. |
| `subjectFields: [legalName]` with a template rendering `{{dateOfBirth}}` | Renders an empty field into a legal letter. |

Also: `active` is **not** in `required`, and JSON Schema `default: false` is annotation-only — validators
never apply it. A playbook omitting `active` is valid, so the loader must treat absent as false explicitly.

**C3 · Idempotency is specified three incompatible ways, and the strictest one kills the flagship.**

- `docs/03`: `idempotencyKey` **unique on `userId+controllerId+requestType`** (a DB constraint — absolute, forever)
- `docs/04` step 2: refuse only if an **open/complete** request exists (state-conditional)
- state machine invariant 5: the check happens at **`dispatch`** — but the diagram puts `guardFail(idempotency)` at **`DRAFT`**

Three concrete failures follow from the DB-unique reading:
1. **The provenance chain breaks.** `PROMPT-PIVOT` step 2 spawns `OBJECTION_ART21` at az-direct when
   provenance names it. If the user already ran the M1 Werbewiderspruch to az-direct, the follow-up is
   blocked and lands in `CLOSED_FAILED` — silently killing the flagship's payoff step.
2. **The resend path self-blocks.** `NEEDS_HUMAN --humanResolve:resend--> READY --dispatch-->` re-checks
   idempotency against an open request: itself.
3. **Lawful annual re-access becomes impossible.** Art. 15 can be exercised repeatedly; a permanent unique
   constraint forbids it.
   *The key needs a time or supersedes dimension.* `CLAUDE.md` §8 says "may not be sent twice **by accident**" —
   which the DB constraint over-enforces into "may not be sent twice, ever."

**C4 · The flagship's core escalation lever has no transition.** Both provenance playbooks set
`escalation.onIncompleteSourceList: DRAFT_ART77`, resting on the BayLDA precedent that an incomplete
Art. 15 answer is itself a violation. But an incomplete answer is neither `complied` nor `refused`, so it
lands in `NEEDS_HUMAN` — and **there is no `NEEDS_HUMAN → ESCALATION_DRAFTED` edge.** The reviewing human
can only: mislabel it `REFUSED` (corrupting the per-controller stats that `docs/02` calls the moat and
`docs/05` §7 later publishes as facts), or `resend` and wait another 30 days. The graph's only path from
`NEEDS_HUMAN` to escalation is a full resend-and-expire loop.

**C5 · `BLOCKED_IDENTITY` is a dead end.** It is described as *"terminal until identity resolves"* but the
transition table gives it **no outbound edge at all**. A user who verifies after being blocked cannot
proceed; the request is stuck forever. Directly violates the usability gate's "no dead-end screens, every
screen states the next action."

**C6 · Every template promises an enclosure that nothing in the system can produce.** All three say the
user encloses a redacted ID (*"füge ich … eine geschwärzte Ausweiskopie bei"*), and `identityProof.required:
true` on 3 of 5 playbooks. But `docs/03`'s `Identity` entity holds only
`status, method, legalName, dateOfBirth, addresses[], verifiedAt, providerRef` — **no ID document, no
redaction pipeline, no artifact reference.** The letters will be rejected for failure to identify, which
burns the 30-day clock and records a false "non-compliant controller" statistic against the census.
`docs/08` Tier 2 calls this the "pre-verified identity packet" but no entity backs it.

### High

- **H1 · No late-response path.** `ESCALATION_DRAFTED → RESPONSE_RECEIVED` and `ESCALATED →
  RESPONSE_RECEIVED` do not exist. Controllers routinely answer past the one-month clock, and a DPA
  complaint frequently *prompts* the late reply. Neither can be recorded.
- **H2 · `channel.registered` is one boolean for a two-channel config.** `loeschung.generic-adresshaendler`
  has `primary: email` + `registered: true` — Einwurf-Einschreiben by email is not a thing. `registered`
  must be per-channel, and the schema must reject it on `email`/`web_form`.
- **H3 · `ROBINSON` and `EINMELDUNG_FRAUD` are not rights requests.** A DDV Robinsonliste enrolment and a
  Schufa fraud victim marker have no Art. 12(3) clock and no Art. 77 remedy — you cannot complain to a DPA
  that an industry opt-out list was slow. Yet the schema **requires** `deadlineDays` and `escalation` on
  every playbook, forcing both to declare a fictional statutory deadline. `docs/08` already models
  suppression correctly as separate `SuppressionProgram`/`SuppressionEnrolment` entities with
  `renewalMonths` — the two models conflict.
- **H4 · The milestone plan predates the pivot.** `docs/09` declares Provenance the flagship and says
  "the working provenance request is the highest-return milestone" — but `docs/01-mvp-scope.md` has **no
  milestone for it**, no acceptance criterion mentioning `ACCESS_ART15_SOURCE`, and README's "What Phase 0
  is" still lists the pre-pivot scope. `docs/01` M2 also targets "the 3 credit bureaus" incl. Boniversum,
  while `docs/09` says Boniversum merged into infoscore in Sep 2025 and to route there. Whoever follows
  `docs/01` builds the wrong thing.
- **H5 · The templates are not sendable letters.** They begin at `Betreff:` — no sender block, no
  recipient block, no place/date line, no signature. `{{today}}` has no format spec (German formal letters
  need `TT.MM.JJJJ` or "Ort, den 7. August 2026"). `{{primaryAddress}}` / `{{additionalAddresses}}` have no
  derivation rule from `Identity.addresses[]`. A postal Art. 15 to a bureau with a typed-not-signed name is
  routinely rejected.
- **H6 · Enum drift.** `docs/03` lists 4 request types; the schema and `docs/09` define 6
  (`ACCESS_ART15_SOURCE`, `EINMELDUNG_FRAUD` missing from the data model).
- **H7 · `ARCHITECTURE-DECISIONS.md` does not exist** but is referenced by `docs/02` and all three PROMPT
  files, each of which ends with "update ARCHITECTURE-DECISIONS.md".

### Medium / low

- Census slugs referenced by playbooks with no row in `docs/07`: **`infoscore`** (the primary provenance
  target), plus watchlist entries `capaneo`, `regis24`, `postadress`. `docs/09` retargeted the census in
  prose but `docs/07`'s tables were never updated.
- `provenance.infoscore.yaml` cites *"infoscore's own Art. 14 notice (V7, Aug 2026)"* as established fact
  and uses it as an Art. 77 trigger ("if the answer DENIES AZ Direct … flag for a strong Art. 77
  complaint") — with no `TODO(counsel)` on that specific claim, unlike every other factual assertion in
  the file. A legal escalation keyed to an unverified notice version is a liability.
- `docs/04`'s example playbook block shows `identityProof.accepts: [redacted_id]` alongside
  `required: false`; the schema permits `required: true` with `accepts: [none]` (self-contradictory) and
  `full_id` for a bare marketing objection (the over-collection `docs/07` warns against).
- README: duplicate list number "4", and `PROMPT-PIVOT.md` is missing from the repo-layout tree though
  step 3 tells you to use it.
- `version` monotonicity ("never mutate a shipped version") is unenforceable in JSON Schema — needs a CI check.

## 4. The one decision that needs a human

**C1 — when does the statutory clock start?** Two coherent answers, materially different cost and legal posture:

- **(a) Registered post for anything that can escalate.** Legally clean; matches `CLAUDE.md` §6 verbatim.
  Cost: `docs/06` H7 prices Einwurf-Einschreiben at €3.30, so every escalatable request is a €3–5 action,
  not a €0.50 one — and *all five* current playbooks escalate on deadline expiry.
- **(b) Email starts the clock; registered post only when escalation is actually drafted.** Preserves the
  cost model. Requires deleting the "email is not proof" line from `CLAUDE.md`/`docs/05` and accepting
  that the first deadline assertion rests on a DKIM accept.

**Recommendation: (b), with the guardrail rewritten rather than quietly contradicted** — send by email,
set a *provisional* `deadlineAt`, and require a registered re-send with QTSP anchoring before any
`ESCALATION_DRAFTED` transition. That keeps the cheap path cheap and puts the provable send exactly where
the law needs it. But this is your call, and `CLAUDE.md` must be edited to match whichever you pick —
right now the two normative files disagree and the implementer will pick one at random.

## 5. Recommended sequence

1. **Fix B1/B2 and the doc-integrity items** (~1 hour, mechanical, no decisions).
2. **Resolve C1 in `CLAUDE.md`**, then reconcile C3–C6 in the state machine and data model. These are spec
   edits, not code — doing them after the scaffold exists means rewriting the state machine and migrating
   Prisma.
3. **Harden `playbook.schema.json` until `negative.mjs` rejects all 23 holes**, and promote the three
   harnesses to CI. This is the cheapest high-leverage code in the repo (~200 lines) and it is the layer
   that stops a malformed legal letter from being generated at scale.
4. **Then scaffold** — but against `docs/09`'s flagship (a working `ACCESS_ART15_SOURCE` path end to end),
   not `docs/01`'s stale milestones. Update `docs/01` and README to match, or delete their scope sections
   and point at `docs/09`.

Rationale for ordering spec-before-code: every C-item is a contradiction between two documents that a
coding agent will resolve silently and arbitrarily. Fixed now they cost an hour of editing; fixed after
session 1 they cost a state-machine rewrite, a Prisma migration, and a re-review of anything already sent.
